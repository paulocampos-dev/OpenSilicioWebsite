Cursos: structure and mocks

Cursos

A fourth public tab. Its own content type, three levels deep, video as first-class data, and reader-visible progress. Below: how it works, then seven mock screens across three decision points. Pick one letter per decision.

How it works

Schema

cursos
  id           uuid pk
  slug         varchar unique
  titulo       varchar
  descricao    text          -- one line, for the card
  ementa       text          -- Lexical: o que você vai aprender
  image_url    text
  nivel        varchar       -- Iniciante | Intermediário | Avançado
  publicado    boolean
  created_at, updated_at

curso_modulos
  id           uuid pk
  curso_id     uuid  -> cursos on delete cascade
  ordem        int
  titulo       varchar
  resumo       text  null

curso_aulas
  id           uuid pk
  modulo_id    uuid  -> curso_modulos on delete cascade
  ordem        int
  slug         varchar       -- unique within the curso
  titulo       varchar
  video_url    text  null
  duracao_seg  int   null
  conteudo     text          -- Lexical JSON
  publicado    boolean

API

GET /api/cursosList with aggregate counts (módulos, aulas, duração total). One query with a lateral join, not N+1.
GET /api/cursos/:slugCurso plus the full módulo/aula tree, titles and durations only. The whole syllabus in one request; no aula bodies.
GET /api/cursos/:slug/aulas/:aulaOne aula with its body, plus previous/next.
admin CRUDCurso, módulo and aula, plus a reorder endpoint that takes an ordered id list per level.

Frontend routes

/cursosindex
/cursos/:slugsyllabus
/cursos/:slug/:aulaaula

Progress, without accounts

There are no public logins, only the admin JWT. So progress lives in the visitor's own browser: one localStorage key, per curso, holding completed aula slugs and the last one opened. 

opensilicio-cursos-progresso
{ "do-rtl-ao-gds": { "concluidas": ["o-que-e-um-pdk", "instalando"], "ultima": "primeiro-verilog" } }

Consequences worth accepting up front: progress does not follow the reader across devices, a cleared browser wipes it, and it is invisible to you as an author (no completion analytics). Everything renders correctly at zero progress, so the feature degrades to nothing rather than breaking.

Three things that need care in this codebase

Wiki links content_wiki_links.content_type has a CHECK constraint of ('blog','education'). Wiki terms inside an aula need a migration to widen it to 'curso_aula', plus the matching literal in the frontend types and the WikiLinkInserter. Otherwise aulas silently cannot carry wiki terms.
Lexical nodes The aula body reuses LEXICAL_NODES unchanged, so YouTube, WaveDrom, seven-segment and equations all work in aulas on day one. The editor and the read-only renderer must register the identical set, as they do today.
Deleting Cascade runs curso → módulo → aula. Deleting a curso deletes every aula body under it. The admin needs a typed confirmation, not a one-click delete.

Decision 1: the /cursos index

Where the new tab lands. Three courses shown, one of them partly read.

A

Card grid, parity with Educação

Exactly the pattern already on /educacao: duotone photo, tag, condensed title, description, meta line. Progress is a hairline under the photo. Zero new visual vocabulary, and the two tabs read as siblings.

Decision 2: the course page

The syllabus. Where a reader decides to start, and where they see the whole shape of the thing.

D

Single column, syllabus front and centre

Header, then the módulo tree at full width. The aula list is the page. Long courses stay readable because each módulo is its own titled block with a rule above it. Metadata sits in one meta strip instead of a panel.

Decision 3: the aula page

Video first, notes under it. The question is whether the course tree stays on screen.

F

With a spine

A fixed left column holds the whole course: módulos, aulas, ticks, current highlighted. You always know where you are and how much is left, and moving between aulas never routes back through the syllabus. This is the option you did not pick in the questions, shown so you can judge it rather than imagine it. Cost: a new layout that no other page on the site uses, and a mobile fallback (drawer or collapsed strip).

What to pick

Three letters

Index: A, B or C.
Course page: D or E.
Aula page: F or G.

My leaning

C, D, G. C because progress data only earns its keep if it shortens the path back in. D because the syllabus is the product and a sticky panel steals width from a list that wants to be wide. G because it is the layout the site already has, so the first version ships without inventing a second page architecture, and the spine can be added later without touching the data model.

Open questions, smaller

How does an aula get marked done? Manual button, or automatic when the reader reaches the foot of the page. Manual is honest and predictable; automatic is friendlier but marks things done that were skimmed. Manual can be added to automatic later, not the reverse.
Do aulas show up in Educação, search, or the wiki backlinks? If yes, aulas need the wiki CHECK constraint widened and a place in whatever list Educação renders. If no, Cursos is a sealed section and the two libraries never mix.
What happens to the existing 04 to 19 trilha? It stays in Educação untouched, gets copied into a curso, or gets moved. Moving is the cleanest result and the most work, and it changes live URLs that may already be linked.
Publishing granularity Can a curso be published with some aulas still drafts, showing them locked or hidden in the syllabus? Or is a curso all or nothing? This decides whether you can release módulo 1 while writing módulo 4.
Where do videos live? YouTube embeds (free, already supported by the Lexical YouTubeNode, but off-platform) or self-hosted mp4 through the existing upload path (50 MB cap today, and the VPS serves the bytes). This one changes the infrastructure answer more than the design.

One thing I noticed while reading the tokens

In dark mode the steel ramp is deliberately not flipped, so --color-accent-ink stays #416180 on the #16222e ground. Anywhere it carries text, such as the active resource tab in Recurso.tsx, contrast lands around 1.6:1. The mocks above use a lighter step in dark so they read. Not part of this feature, but worth a look sometime.
